## R1. Cowrie's `head` rejects `head -1`

**What:** Cowrie 3.0.14's `head` prints `head: invalid option -- '1'` for `head -1`. Real GNU head accepts
the obsolete `-NUM` form, and bots use it often (`cat /etc/passwd | head -1`). This is a fingerprint.
The router marks `head` as deterministic (it is in `KNOWN_COMMANDS`,
`src/vulnmaze/router/known_commands.py:18`), so the LLM gap-filler can never cover for it.

**How to find:** start the stack, then in an interactive SSH session:

```bash
ssh -p 2222 root@127.0.0.1
cat /etc/passwd | head -1
```

Observed in the 11 Oct smoke test: `head: invalid option -- '1'`.

**Suggested fix:** add a fixed handler in `src/vulnmaze/cowrie_ext/commands.py` that rewrites `-NUM` to
`-n NUM` and then defers to Cowrie's `head`, the same pattern as `Command_sudo`. Check other Cowrie
commands for the same gap (for example `tail -1`).

## R2. Leak filter rejects real output that starts with "OK", "Okay" or "Sure"

**What:** `S1C_PREAMBLE` (`src/vulnmaze/llm/sanitize.py:122-126`) treats any stdout whose first line starts
with `ok`, `okay`, `sure`, `alright` and similar as a chatty LLM preamble. Real programs print `OK` first
(`redis-cli set k v`, some health checks), so those answers are rejected and replaced with a fallback
error. This fails safe (no leak), but it lowers fidelity and inflates rejection counts in `llm_calls`.

**How to find:**

```bash
uv run python -c "from vulnmaze.llm.sanitize import tells; print(tells('OK\n', ''))"
```

Prints `['tell_s1c_preamble_stdout']`; it should print `[]`.

**Suggested fix:** only flag `ok`/`okay`/`sure` when followed by a comma, an exclamation mark or more
prose (for example `^\s*(?:sure|okay|ok)[,!]`), and add a test case for bare `OK`.

## R3. `state-api` service runs but nothing calls it

**What:** the docstring at `src/vulnmaze/state/api.py:3` says the LLM gateway is its first client, but the
gateway opens `StateStore` directly on Postgres (`src/vulnmaze/llm/gateway.py:253-309`). No code calls
the HTTP API, yet the container runs (`infra/docker-compose.yml:120-136`) and needs
`VULNMAZE_STATE_TOKEN`.

**How to find:**

```bash
git grep -n -E "state-api|:8081|VULNMAZE_STATE_TOKEN" -- src infra
```

The only hits are the service definition, its own code and the env example: no client.

**Suggested fix:** either remove the service and token (smaller attack surface, simpler manual), or keep
it as the documented interface for the Machine Learning (ML) layer and say so in the README and report.

## R4. Files referenced in docstrings do not exist

**What:**
- `src/vulnmaze/router/known_commands.py:3` says the list is generated by `scripts/export_known_commands.py`. There is no `scripts/` folder.
- `src/vulnmaze/llm/evaluation.py:3` says it runs the golden command set through the gateway and writes a CSV. Only the helpers (`load_golden`, `summarise`, `score`, `cohen_kappa`) exist; there is no runner and no golden YAML file.
- `src/vulnmaze/ingest/public.py:12` asks for fixtures under `tests/fixtures/public/`, which did not exist.
- `src/vulnmaze/digest/builder.py:9` mentions a golden-file test, which did not exist.

**How to find:**

```bash
git grep -n -E "export_known_commands|tests/fixtures/public|golden" -- src
git ls-tree -r --name-only 26d38ed | grep -E "^(scripts|tests)/"
```

The second command prints nothing at `26d38ed`.

**Suggested fix:** ask the repo author whether these exist locally (they were likely under the then
git-ignored `dev/`) and commit them, or write them. The evaluation runner and golden set are needed for
plan task T12 (fidelity metrics).

## R5. Usernames are stored without de-identification

**What:** `normalise` stores `username` as typed (`src/vulnmaze/ingest/normalize.py:126`), and the digest
keeps it per login attempt. Attackers and users sometimes type a password or personal name into the
username field, so a released dataset could contain secrets or personal data.

**How to find:**

```bash
git show 26d38ed:src/vulnmaze/ingest/normalize.py | sed -n 120,130p
```

**Suggested fix:** before any dataset release (plan task T19), either HMAC usernames that are not in a
list of common service accounts, or scrub them in the export step only.

## R6. Security-floor constants duplicated across modules

**What:** the standard bin directories are defined three times and the command-name pattern twice:

- `src/vulnmaze/cowrie_ext/escalation.py:35-36` (`BIN_DIRS`, `_NAME`)
- `src/vulnmaze/cowrie_ext/hooks.py:36` (`BIN_DIRS`, as a tuple)
- `src/vulnmaze/llm/gateway.py:67-68` (`BIN_DIRS`, `COMMAND_NAME`)

If one copy changes and the others do not, Cowrie and the gateway disagree about which commands may be
escalated.

**How to find:**

```bash
git grep -n -E "^BIN_DIRS|_NAME = re.compile|COMMAND_NAME = re.compile" -- src
```

**Suggested fix:** define both once in `src/vulnmaze/router/rules.py` and import them.

## R7. Digest timing list grows without a cap

**What:** commands are capped at `MAX_COMMANDS_KEPT = 2000` (`src/vulnmaze/digest/builder.py:24`), but
`timing.gaps_s` is appended for every typed command without a limit (`builder.py:145`). Long bot sessions
make the JSONB digest grow without bound, and the digest is rewritten on every batch.

**How to find:**

```bash
git show 26d38ed:src/vulnmaze/digest/builder.py | sed -n 140,150p
```

**Suggested fix:** keep running mean and variance (Welford's method) plus at most the first N gaps.

## R8. Ingester health check always passes

**What:** `infra/docker-compose.yml:117` checks `os.kill(1, 0)`, which only proves process 1 exists.
A stalled ingester (for example the uncommitted-transaction bug fixed in v0.6.1) still reports healthy.

**How to find:**

```bash
git show 26d38ed:infra/docker-compose.yml | sed -n 112,118p
```

**Suggested fix:** have the ingester touch a heartbeat file after each poll and check its age, or check that
`ingest_checkpoints.updated_at` moves while `cowrie.json` grows.

## R9. Ollama image unpinned

**What:** `infra/docker-compose.yml:168` and `:188` use `ollama/ollama:${OLLAMA_TAG:-latest}`, and
`infra/.env.example:37` sets `OLLAMA_TAG=latest`. Results can change between runs without any code
change, which matters for reproducible evaluation numbers.

**How to find:**

```bash
git grep -n -E "OLLAMA_TAG|ollama/ollama" -- infra
```

**Suggested fix:** pin the version used for the evaluation runs and record it in the report.

## R10. Pipeline image built four times under different names

**What:** `ingester`, `state-api`, `llm-gateway` and `probe` each have their own `build:` block for the same
Dockerfile (`infra/docker-compose.yml:105`, `:123`, `:141`, `:205`), so Compose produces four identically
built images with different names. Build cache hides the cost, but it wastes disk space and clutters
`docker images`.

**How to find:**

```bash
docker compose -f infra/docker-compose.yml build
docker images | grep vulnmaze
```

**Suggested fix:** build once with `image: vulnmaze/pipeline:local` on one service and reference that image
from the others.

## R11. State API token comparison (fixed)

**What:** `src/vulnmaze/state/api.py` compared the bearer token with `!=`, which leaks timing information.
The gateway already used `secrets.compare_digest`.

**Status:** fixed in the uv/tests PR by switching to `secrets.compare_digest`.
