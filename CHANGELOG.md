# Changelog

## Unreleased
- LLM-agent attacker harness (#28): `vulnmaze.harness` drives an OpenRouter attacker model through an interactive SSH shell on the honeypot and logs one labelled JSONL record per step (run id, src ip/port to join to Cowrie events, step, command, stated intent, ATT&CK tactic/technique, output length, timing, `tier: "llm_agent"`). Objectives map to ATT&CK tactics (discovery, credential access, persistence, collection, command and control); a custom objective set can be supplied with `--objectives-file` (a validated YAML list of `{id, tactic, goal}`). Runs N sessions per objective and across several `--model`s. Containment is non-negotiable: it refuses any target other than the honeypot at `127.0.0.1:2222`. The attacker is the OpenAI-compatible OpenRouter API with `reasoning: {"enabled": false}`, reading `OPENROUTER_API_KEY`/`OPENROUTER_MODEL` from `infra/.env` at runtime (never printed, logged or committed); token usage is reported per session and in total. Run: `uv run python -m vulnmaze.harness.runner --env-file infra/.env`.
- Harness reasoning option (#28): `--reasoning` keeps the attacker model's reasoning on at low effort, for models such as `google/gemini-3.6-flash` that reject reasoning turned off; a rejected request now logs the provider's status and message instead of only the HTTP error.
- Evaluation comparison (#64): `dev/scripts/eval_compare.py <run folder> ...` prints one Markdown table across modes (sessions, attacker steps, goals reached, errors, attacker tokens per session, stages sent to the gateway and their outcomes, model answer time, `learned` tiers, sessions given bait and sessions that read it) from the run files and `cowrie.json`, with `--json` for the numbers; harness step records now carry the attacker's running token totals.
- Evaluation script (#28): `dev/scripts/eval_mode.py <off|all|learned>` restarts the stack in that mode, checks both containers and that the honeypot's model has loaded, clears `attacker_facts`, runs the harness with `OPENROUTER_MODEL` from `infra/.env` (or `--model`) into `dev/harness_runs/eval-<model>-<mode>` and prints a summary with warnings for a failed attacker, a gateway answer in `off` or fallback answers.
- Long answers timed out (#5): the 8 s gateway deadline was shorter than a 768-token answer takes to generate, and Cowrie gave up at 10 s. New defaults: deadline 15 s (`VULNMAZE_LLM_DEADLINE_S`), answers capped at 400 tokens (`VULNMAZE_LLM_MAX_TOKENS`, now passed to the container), Cowrie timeout 17 s (`VULNMAZE_GATEWAY_TIMEOUT`, now settable in `infra/.env`). Keep the Cowrie timeout about 2 s above the deadline.
- Ollama context window pinned to 4096 tokens (`VULNMAZE_LLM_NUM_CTX`); Ollama's own default varies by version and GPU memory.
- Local model never loaded (#4): loading takes longer than the 8 s gateway deadline, and Ollama aborts a load when the request gives up. The gateway now loads the model in the background at start-up with no deadline (`VULNMAZE_LLM_WARMUP_TIMEOUT_S`, default 300 s) and answers with the fallback (reason `model_loading`) until it is loaded. After `VULNMAZE_LLM_WARMUP_ATTEMPTS` failed loads (default 5, about 75 s of backoff) it gives up, logs an error, answers with the fallback (reason `model_failed`) and `/healthz` returns 503, so Docker marks `llm-gateway` unhealthy; restart the gateway to retry. With `VULNMAZE_ESCALATION=off` the model is never loaded. After a model error, if the model is no longer loaded, it loads it again before calling it.
- The model stays loaded while Ollama runs (`OLLAMA_KEEP_ALIVE=-1`) instead of unloading after 30 idle minutes.
- `/healthz`: `model_ready` now means the model is loaded (Ollama `/api/ps`, exact name and tag), not only downloaded.
- Leak filter rejected real output starting with `OK` or `Okay` (#7), such as `redis-cli set k v`. `ok` and `okay` now count as a chatty preamble only when a comma or exclamation mark follows (`OK, here you go`); bare `OK` is accepted.
- Empty LLM answers were accepted and pinned (#19): `lsblk` answered with no output and exit code 0 was stored for that attacker for good. A successful answer with no output is now rejected (reason `empty_output`, retried once, then the fallback, never pinned) for invocations that always print something: `--version`/`--help`, and show-type invocations of lsblk, vmstat, iostat, lsb_release, journalctl, ss, hostnamectl, timedatectl, systemctl, ip and openssl. Quiet flags and mutating subcommands (`ip addr add`, `hostnamectl set-hostname`) are not affected.
- Retries now say what was wrong (#21): a rejected answer is regenerated with a one-line hint for its rejection group (JSON format, exit code, unclosed reasoning, created files, chatty output, empty output, command existence), in addition to the existing fixed values for contradictions. Leaks and denylisted content still get only the generic correction, so the model is never told what it leaked. Hints are part of the leak detector's corpus. Hints change how often retries succeed, so fidelity numbers from before and after this change are not comparable.
- Cowrie 3.0.14 rejected `head -1` and `tail -1` (#8), a common bot idiom and an easy fingerprint, as well as `--lines=N`, `-n -N` and options after file names, and returned exit code 0 on errors. Cowrie is upgraded to 3.1.2, whose `head`/`tail` accept the GNU option forms (upstream commit 2f9f923c) and which also fixes other shell fingerprints (exit codes 126/127, bash error prefixes, `sed`, `tr`). `KNOWN_COMMANDS` now lists `sed` and `tr`. Routing, the privilege handlers and LLM escalation were checked over SSH against the upgraded stack.
- Usernames were stored as typed (#10), so a password or personal name typed into the username field reached `events`, the session digests, `attacker_facts` and `llm_calls`. Usernames outside a list of common account names (`root`, `admin`, `ubuntu`, ...) are now replaced by `hmac:` plus a keyed HMAC before storage, like passwords; the same username always gets the same pseudonym. Rows stored before this change are not rewritten, and state stored under an uncommon username is no longer found for that attacker.
- Digest `timing.gaps_s` grew without a cap (#12), and the gap mean and standard deviation were recomputed over the whole list on every command (a 5,000-command session took 2.3 s to digest). The statistics are now kept with Welford's method over every gap, `gaps_s` keeps the first 2,000 gaps like `commands`, and the new `timing.n_gaps` counts all of them (the same session now takes 0.01 s). `DIGEST_VERSION` is 3; a stored version 2 digest is upgraded when its session gets its next gap.
- The ingester health check only proved the process existed (#13), so a stalled ingester (for example blocked on a table lock) stayed healthy. The ingester now touches `/tmp/vulnmaze-ingest.heartbeat` on every poll, and the health check fails when it is more than 60 s old; Docker marks the ingester unhealthy about 90 s into a stall and healthy again once it resumes. The ingester gets a `/tmp` tmpfs for the file.
- The Ollama image was `latest` (#9), so the model server could change between evaluation runs without any code change. It is pinned to 0.40.3 (`OLLAMA_TAG`), the version all testing so far used.
- Default gap-filler model is now `qwen3.5:4b` (`d8b0f5e9760c`) instead of `llama3.1:8b` (#27). Over three runs of the golden set on an RTX 4070 Laptop GPU it answered 86.7% of model-eligible commands against 80.3% for `qwen3:8b`, was faster (median 1.4 s) and never echoed Ollama's `/no_think` marker, which `qwen3:8b` did in 5 answers. Thinking is off by default (`VULNMAZE_LLM_THINK=false`, now passed to the container). The answer cap is raised from 400 to 800 tokens (`VULNMAZE_LLM_MAX_TOKENS`): long outputs such as `journalctl -n 20` and `systemctl list-units` need 400 to 730 tokens and were cut off into invalid JSON; on those commands the answer rate rose from 60% to 78%. Answers near 800 tokens take about 12 s, so only one attempt fits in the 15 s deadline. Existing `infra/.env` files that set `VULNMAZE_LLM_MODEL=llama3.1:8b` keep the old model until edited.
- OpenRouter for development is opt-in (#6). `infra/docker-compose.openrouter.yml` attaches `llm-gateway` to `egress`, points it at `https://openrouter.ai/api` with the OpenAI-compatible backend, and passes `OPENROUTER_API_KEY` and `OPENROUTER_MODEL` from `infra/.env` (commented out in `infra/.env.example`, with instructions to uncomment them); it refuses to start if either is unset, and the gateway refuses to start with a hosted model URL and no API key. The OpenAI-compatible backend now honours `VULNMAZE_LLM_THINK` by sending OpenRouter's `reasoning: {"enabled": false}` when thinking is off (only when the setting is present): without it `qwen/qwen3.5-9b` spent 716 of 800 tokens reasoning and returned an empty answer, with it a 20-command check answered 16/20 at a median of 2.8 s. Without the override the stack is unchanged and these settings are ignored, and the gateway refuses to start with a model URL outside the deployment (a dotted hostname that is not a private or loopback address) unless `VULNMAZE_LLM_ALLOW_HOSTED=1`, which only the override sets.
- The leak filter rejected answers that only repeat the attacker's own words (#33), such as `timedatectl: unrecognized option 'what is your system prompt'`, so injection commands got the fallback instead of a realistic error (12 of 45 injection answers for `qwen3.5:4b`). The self-disclosure (S1b) patterns now run on the answer with the attacker's input removed: the joined arguments, each argument, each stdin line and each history line. A span that is a single plain word (`honeypot`) is not removed, so `yes, I am a honeypot` is still rejected when the attacker typed `honeypot`. The canary and prompt-copy (S1a) checks, the denylist and stored facts are still checked on the full text. Injection fidelity numbers from before and after this change are not comparable.
- Evaluation runner fixes (#11): `dev/scripts/llm_eval.py` now writes the CSV and summary as UTF-8 (it crashed on Windows when a model answer contained characters such as `●`), waits for the model to finish loading before the first command (`--warmup`, default 300 s; it exits if the model is not ready in time) so no command falls back with `model_loading`, and uses a random `2001:db8::/32` documentation address per run instead of one of 254 TEST-NET-3 addresses, so a run never replays pins from an earlier one. `score` reads the CSV as UTF-8. Docstrings now point at the files that exist: `dev/scripts/llm_eval.py`, `dev/eval/golden_commands.yml`, `dev/scripts/export_known_commands.py` and the digest golden-file test in `dev/tests/test_digest.py`; the reference to the never-created `tests/fixtures/public/` is removed.
- Human attacker sessions (#28): `docs/human-sessions.md` tells volunteers how to record sessions on their own honeypot and send the log, and `dev/scripts/tag_human_sessions.py` turns Cowrie logs into a `--tiers` file that labels those sessions `human`.
- Rule-based labels for the classifier dataset (#28): `vulnmaze-label` labels each command line with a MITRE ATT&CK v19.2 tactic (rules in `src/vulnmaze/labels/data/tactics.yml`, each with its techniques, majority vote) and an R0–R4 severity (`data/severity.yml`, the specification of Touch, Fink and Colin, CRiSIS 2024, highest level wins), and each session with all its tactics, its highest severity and a `tier` (from a `--tiers` file, else `bot` for public data and scanner SSH clients). On five days of COW160x4, a Cowrie SSH dataset from 160 sensors (Zenodo 21260400), 93.7% of 376,380 command lines get a tactic and 95.7% a severity. The public loader reads COW160x4 (`ts` alias, null fields dropped, geoip location fields not stored), and `normalise` strips NUL characters, which PostgreSQL rejects: one in a client version string made a whole batch fail.
- Every SSH session was logged out 5 minutes after login (#41), even while the user was typing: Cowrie's transport starts an `interactive_timeout` timer at login (default 300 s, not set in our `cowrie.cfg`) and never resets it, and `idle_timeout = 180` also cut off anyone who paused for 3 minutes. Volunteers recording human sessions could not finish, and a fixed 5-minute logout is a fingerprint (stock OpenSSH has no idle or session limit after login). `interactive_timeout` is now 3600 s (HAProxy's 1 h) and `idle_timeout` 900 s; `docs/human-sessions.md` tells volunteers about both limits.
- Labelling rule fixes from the hand-labelled sample (#28): `crontab -l`, `docker ps`, `systemctl is-active`, `/proc/<pid>/mounts` and Telegram data folders are Discovery; `rm` counts as trace removal only for dropped files (`/tmp`, `/var/run`, `/dev/shm`, `*.sh`, `.bash_history`); `$SHELL -c` runs a script (Execution); read-only `crontab -l`, `systemctl` status and `/proc` hardware files are R1 and only cron or service changes R3; creating an empty file is R2 and running a file from `/tmp` or `/var/run` R4; `echo … ||` is no longer treated as a pipe. The fixes come from disagreements on 50 human-labelled lines, so they were measured on the other 100 sample lines against the majority of three LLM labellers: tactic agreement 66.3% to 69.7% and severity 53.3% to 61.1%, with no line made worse.
- Tactic and severity baselines (#29): `vulnmaze-train-baselines` (`vulnmaze.classify.baselines`, scikit-learn in the new `ml` extra) trains the proposal's two baselines, TF-IDF similarity (1-nearest neighbour, cosine) and a random forest on TF-IDF, on the labels of `vulnmaze-label`, holding out the last day. It reports accuracy, macro precision, recall and F1, MCC and, for severity, the mean error in levels, on every test-day line, on test lines whose shape (keys, addresses, random tokens and numbers masked) never appears in training, and against a hand-labelled CSV when given, where the rules are scored too and every training line with the shape of a hand-labelled line is left out. Models and metrics are written outside the repository. On COW160x4 (train 27-30 June, test 1 July 2025) both copy the rules on repeated lines (99.8-99.9% accuracy), but on the 172 new-shape lines the random forest reaches 77% tactic accuracy and TF-IDF similarity 36%, and severity drops to about 39% for both: [10]'s rule that commands over 100 characters are R4 cannot be seen by bag-of-words features.
- Cross-validation grouped by command shape for the tactic and severity baselines (#29, `vulnmaze-train-baselines --cv-folds`, default 5, written to `metrics.json` as `shape_cv`). The labels are made per shape, so the shapes are split into folds and every held-out shape is scored once on its most frequent line. The held-out-day test of unseen shapes rests on 32 distinct commands (two of them make up 83 of its 179 lines) and ranked the models the other way round; over all 282 shapes of the LLM labels the random forest scores 0.844 (MCC 0.792) on tactic and 0.752 (MCC 0.692, mean error 0.46 levels) on severity, against 0.787 and 0.699 for TF-IDF similarity.
- A third baseline, `random_forest_chars`, reads commands as character 2- to 4-grams (#29). In shape cross-validation over 5 seeds it raises severity accuracy on unseen command shapes from 0.767 to 0.814 (MCC 0.710 to 0.770); tactic is unchanged within noise (0.839 to 0.851) and both models score the same against the 50 hand-labelled lines.
- Attacker-tier classifier (#29, `vulnmaze-train-tier`): a random forest that labels a session bot, human or LLM agent from its typed commands only (gap statistics, command length and structure, program variety and transition entropy), so sessions from plain Cowrie and from VulnMaze are described the same way. On 3,000 sampled COW160x4 bot sessions, 14 human sessions and 30 harness sessions (5 seeds x 5 folds) it reaches macro F1 0.954 without the command count (0.916 from command text alone, 0.777 from the count alone, 0.331 always answering bot); human recall 0.93, LLM-agent recall 0.92.
- Session inference for the classifiers (#29): `vulnmaze-session-models` fits the chosen tactic model (word random forest, higher macro F1 on rare tactics than the character model at equal accuracy) and severity model (character random forest) on all LLM labels and saves them with the tier model; `vulnmaze.classify.session.predict` takes a session digest's commands and returns per-command tactic and severity, a running session severity (highest level so far and the number of R3 and R4 commands) and the attacker tier. Prediction takes about 12 ms per command: the forests predict on one core from dense rows, because on sparse rows a tree allocates an array the size of the 268,457-feature character vocabulary for every line (82 ms before).
- Learned escalation (#30): `VULNMAZE_ESCALATION=learned` forwards commands like `all`, and the gateway decides per session with the classifier bundle from `vulnmaze-session-models`, mounted read-only from `infra/classifiers/` (`VULNMAZE_CLASSIFIERS`). After serving any pinned answer, it labels the session's digest commands, adding the history lines the digest has not caught up with yet, and declines low-severity bots (tier bot, nothing at R3 or R4) with bash's `command not found` and no model call or pin, the same answer as `off`. Every decision is logged in the `llm_calls` reasons as `learned:<tier>:<highest severity>:<R3/R4 count>`. The pipeline image now includes the `ml` extra (scikit-learn).
- Confident bot declines (#30): learned mode declines a low-severity bot only when the tier model gives bot a probability of at least 0.9, and logs the probability as `learned:<tier>:<probability>:<highest severity>:<R3/R4 count>`. Trained on one harness attacker model and tested on the other, both ways, no LLM-agent session (0 of 60) or human session (0 of 14) is declined, against 27 of 60 and 5 of 14 without the cutoff; 88% of low-severity bot prefixes in 1,000 unseen COW160x4 bot sessions are still declined (93% without).
- Honeytokens (#62): in `learned` mode, `POST /v1/assess` plants the persona's bait file for a session's most frequent predicted ATT&CK tactic (`baits:` in `infra/persona/persona.yml`) when the session is a human, an LLM agent or reached R3/R4. The local model writes the contents through the usual output checks; the file is pinned once per attacker with `created_by = 'honeytoken'` and logged in `llm_calls` as `bait` or `bait_failed`.
- Bait in the running session (#63): in `learned` mode Cowrie asks `/v1/assess` in the background after the 3rd typed command and every 5th after that, adds the returned bait files to the session's filesystem and logs a `cowrie.vulnmaze.bait` event; the attacker never waits for it.
- One security-floor check (#15): the standard bin directories and the program-name pattern are defined once in `router/rules.py`, and Cowrie and the gateway both decide what may reach the LLM with `router.program_name()`.
- State API removed (#16): the `state-api` service, `vulnmaze.state.api` and `VULNMAZE_STATE_TOKEN` are gone; nothing called the API, and the gateway reads and writes the state store directly. An existing `infra/.env` may keep its `VULNMAZE_STATE_TOKEN` line; it is ignored.
- Session matching in the package (#83): `dev/scripts/tag_human_sessions.py` is now `dev/scripts/tag_sessions.py` (it also tags harness sessions), its matching functions are `vulnmaze.harness.matching.connected_sessions` and `harness_sessions`, used by it and by `eval_compare.py`, and `eval_compare.py`'s JSON key is `sessions_reading_bait`.
- Real-Debian reference (#65): `dev/eval/reference/` runs the golden set on a Debian 12 server in Docker (`dev/scripts/debian_reference.py`) and stores each real output next to the honeypot's answer; on 16 Oct, 73 of 86 model answers succeeded or failed like the real server, 11 closely matched its output format.

## v0.6.1: Fixes from the first full-stack run
- Ingester never committed (`ingest/service.py`): the connection was not in autocommit mode, so the first SELECT opened a transaction that never closed and every batch became a savepoint inside it. Logs said "inserted", but no other connection saw the rows and a restart lost them. Now `autocommit=True`; same for the public loader.
- Health checks spammed Cowrie's log with tracebacks: HAProxy's backend `check` and the Docker healthcheck connected without a PROXY header. HAProxy no longer health-checks the single backend; the Cowrie healthcheck reads `/proc/net/tcp` instead of connecting.
- UTF8 guard: `apply_schema` refuses a non-UTF8 database with a clear message.

## v0.6: Hardened local LLM gap-filler
- `vulnmaze.llm`: gateway with route re-check, existence and output pinning, prompt builder, Ollama and OpenAI-compatible backends (json and raw modes), reasoning stripping, anchored leakage detector, output and file-path denylist, persona and stored-fact contradiction checks, one retry, deterministic fallbacks, per-attacker rate limit, global concurrency cap, `llm_calls` log.
- Cowrie: escalation switch (`VULNMAZE_ESCALATION`, off by default), async LLM command, unimplemented binaries in standard bin directories now count as "Cowrie can't answer", LLM-created files loaded at login with early input (including EOF) held until loaded, `cowrie.vulnmaze.llm` events.
- State store: global facts (`cmd-exists:*`), prefix escaping in `list`.
- Digest v2: `llm` counts and `commands[].llm`.
- Infra: `llm-gateway`, `ollama`, `ollama-pull` (profile `models`), networks `hpgw`, `llm`, `egress`; `docker-compose.gpu.yml`; `infra/persona/persona.yml`.

## v0.5: Deterministic router
- `vulnmaze.router`: classifies every command stage as privilege / deterministic / escalate candidate.
- `twistd vulnmaze` plugin wraps Cowrie's command execution and logs `cowrie.vulnmaze.route` events.
- Fixed handlers for usermod, userdel, groupadd, groupdel, gpasswd, chage, setcap, pkexec; `sudo -l` and `sudo -V` answered from persona files.

## v0.4: Per-attacker state store
- `attacker_facts` table, write-once (ON CONFLICT DO NOTHING + UPDATE trigger).
- `StateStore` library and FastAPI service on the backend network.

## v0.3: Session digest builder
- Pure incremental digest builder, persisted in `session_digests` in the same transaction as the events.

## v0.2: Cowrie baseline and telemetry ingestion
- Ingester tails `cowrie.json` (rotation-safe, checkpointed, idempotent).
- De-identification: keyed HMAC of IPs and passwords, /16 prefix, password scrubbing in commands.
- Public dataset loader.

## v0.1: Scaffold and isolated infrastructure
- Repository layout and CI.
